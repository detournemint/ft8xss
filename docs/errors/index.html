Transmit state

TX is off — click Call CQ, or a station, to transmit

Nothing is wrongnormal

WSJT-X's Enable Tx is off, and it has been for more than 30 seconds. This is the resting state of a correctly configured station: ft8xss does not arm the transmitter by itself, so between QSOs Enable Tx sits off until you ask for something.

It is worth saying out loud only because the failure it prevents is silent — thinking you are calling when nothing is going out. Click Call CQ, or call on any decode, and the transmitter arms as part of that action.

Cause
Enable Tx is off and auto-arm is disabled (the default).
Do
Nothing, unless you meant to be transmitting.
TX has been off for 72s — automatic re-arm did not take

Auto-arm is on, but Enable Tx would not stay oncheck

You have Auto-arm transmit switched on, so ft8xss tried to put Enable Tx back after a QSO closed — WSJT-X drops it automatically — and it is still off half a minute later. Something is stopping the keystroke landing.

Enable Tx is a checkbox with no UDP message behind it, so the only way to set it is to send Alt+N to the WSJT-X window. That fails if the window cannot be found, if the title in your settings does not match the real one, or if xdotool is not installed.

Check
The Radio panel — if it says automation is unavailable, start at that entry instead.
Check
FT8XSS_WSJTX_WINDOW matches your real window title.
Do
Press Enable Tx in the banner, or set it in WSJT-X. Consider turning auto-arm off: with CQ selected it means the station transmits unattended.

If you saw “auto-recovery failed” instead, you are running a build from before this was corrected. That wording appeared even when auto-arm was switched off and nothing had been attempted, and on many stations the re-arm could never have worked in the first place — it looked for a window titled WSJT-X MOD rather than yours. Update.

TX is off — enable it in the WSJT-X window

ft8xss cannot set Enable Tx herenormal

The same state as above, on a station without GUI automation. ft8xss can tell you Enable Tx is off but cannot switch it on, because there is no UDP message for that checkbox. Tick it in WSJT-X yourself.

Everything else — decodes, calling, logging, upload, the map — works normally. See automation unavailable.

Nothing is being heard

No decodes for 63s — check radio, audio, or USB

The receive path has stoppedact

FT8 decodes every 15 seconds. On a live band, a minute of silence is not quiet conditions — it is a broken receive chain. The band being genuinely dead is possible but is the least likely explanation.

In rough order of likelihood:

Audio
WSJT-X's input device disappeared or got switched — a USB re-enumeration renames it. Check Settings → Audio in WSJT-X.
Radio
Still on the right band and mode? Someone or something may have moved the VFO, or the rig powered down.
USB
The cable or hub dropped. Look for the serial port disappearing from the diagnostics bundle.
WSJT-X
Stopped or crashed. ft8xss keeps running without it, so the page still looks alive.

Antenna and power

HIGH SWR 5.1 — transmit is blocked (limit 3.0). Run the tuner or check the antenna.

Transmit is refused until the match improvesblocked

A transmission ended with an SWR at or above the limit, so ft8xss has disabled Call CQ, Enable Tx and band setup. This is deliberate: at that mismatch a solid-state final is folding back hard, and repeatedly keying into it is how finals die.

Click Run tuner to cycle the ATU. Tuning keys the radio, so ft8xss measures SWR right through the cycle and lifts the inhibit itself the moment the match comes good — you do not need to transmit to prove it.

If the SWR does not come down, the problem is outside the radio: wrong antenna for the band, a bad connector, water in a feedline, a disconnected coax. Fix that before transmitting.

Override exists for rigs that do not report SWR while their ATU runs, which would otherwise leave the station inhibited with no way out — lifting the inhibit needs a good reading, and a reading needs a transmission. Use it only when you have checked the antenna yourself. It is recorded in the log.

Limit
SWR 3.0, from SWR_ABORT.
Clears
When the tuner measures a good match, when a transmission reads below the limit, or by Override.

If running the tuner never unblocked you, you are on a build from before this was fixed: the tuner ran, and often corrected the match, but nothing re-measured, so the inhibit stayed on with a perfectly good antenna. Update.

40m: 8.0 W of 25 W (4.9 dB low)

You are transmitting far less power than the rig is set forcheck

ft8xss measures every transmission. Here the radio is set to 25 W and only 8 W came out, with ALC low — meaning WSJT-X is not driving the rig hard enough, not that the radio is faulty.

The usual cause is that WSJT-X's Pwr slider is remembered per band. Move to a band you have not calibrated and it inherits whatever the last one used, which can be many dB wrong. That is easy to miss: everything looks normal, you are simply much quieter than you think.

ft8xss can correct this itself. Because applying a change means restarting WSJT-X, it only does so while the station is idle — during a QSO you get a Fix drive button instead. You can also set the drive by hand with the TX drive slider in the Radio panel.

Trips at
Below 70% of the rig's set power.
Note
Moving the TX audio offset a long way changes the drive too — the transmit filter is not flat — so a large move re-opens this check.
40m: ALC 0.98 above 0.3

You are over-driving the transmittercheck

ALC action means the rig is compressing to protect itself. For FT8 — a constant-envelope single tone — any significant ALC is wrong. It flattens the waveform, splatters into your neighbours' passbands and can make you harder to decode despite the wattmeter looking healthy.

Reduce drive, not power: turn the WSJT-X Pwr slider down until ALC barely moves, then use the rig's own power control to set output. ft8xss will suggest a correction, or Setup band will find it by measurement.

Target
ALC at or below 0.30; below 0.20 is better.

QSOs

EA5TT has repeated the same reply to you 3× — it is not receiving your response. Check TX level, or QSY.

They cannot hear youcheck

The other station keeps sending the same message, which means your reply is not getting through. They are transmitting fine; the failure is on your side, and continuing to answer will not fix it.

Most common causes, in order:

Power
You are quieter than you think — see power low. This is the usual one.
Collision
Someone else is transmitting on your audio offset. Find clear slot moves you.
Propagation
Genuinely asymmetric paths exist. If they are weak into you, you are probably weaker into them.
Slot
Transmitting in the same period they are — you would both be deaf to each other.

Who hears me settles it: if PSK Reporter shows nobody hearing you, the problem is your transmit path, not the other station.

Automation and setup

TX enable and band setup must be done in WSJT-X (no window matching 'WSJT-X' on :99)

ft8xss cannot drive the WSJT-X windowlimited

A few things exist only in WSJT-X's interface, with no UDP message behind them: Enable Tx, the Pwr slider, and the Log QSO dialog. To reach those, ft8xss sends keystrokes to the window with xdotool. Without that, everything else still works — decodes, calling, logging, upload, telemetry, the map — but those three are yours to do.

The reason in brackets tells you which case you are in:

xdotool not installed
Install xdotool and xwininfo.
no window matching …
WSJT-X is not running, is on another display, or its title differs. Set FT8XSS_WSJTX_WINDOW.
disabled by FT8XSS_NO_GUI
You turned it off. Unset it.

On a desktop this is often the right arrangement — you are sitting in front of WSJT-X anyway. It matters most on a headless station.

waiting for WSJT-X — it has not sent a packet yet

No UDP traffic has arrivedwait

ft8xss cannot send anything to WSJT-X until WSJT-X has spoken first — it learns where to reply from the packets it receives. Until then, calling and CQ are disabled.

If it never clears, WSJT-X is not sending to this machine and port. In WSJT-X: Settings → Reporting, UDP Server set to this host, port 2237, Accept UDP requests ticked.

One ordering trap catches people: start ft8xss before WSJT-X. If nothing holds the UDP port, WSJT-X binds it itself and ft8xss hears nothing.

a band setup was interrupted; transmit was stopped. Run it again when you are ready.

A calibration died partway throughcheck

Band setup arms the transmitter to take its measurements. This run was cut short — the service restarted, or the process was killed — so on the way back up ft8xss stopped transmitting rather than risk leaving the radio armed and calling CQ with nobody watching.

Nothing is broken. The drive for that band may be part-way between settings, so run Setup band again when you are ready.

SWR 5.1 is too high to transmit safely — run the tuner or check the antenna first

Band setup refused to startblocked

Calibrating drive means transmitting several times. Into a bad match that is a series of avoidable hits on the finals, and the readings would be meaningless anyway — a mismatch makes the power figures lie.

Sort the antenna first: Run tuner, then check the feedline and that the antenna suits the band. See high SWR.

transmitting — wait for the end of the over

The drive change was refused, for nowretry

WSJT-X has no remote control for the Pwr slider, so changing it means editing its configuration and restarting it. Doing that mid-transmission would cut the over in half and can leave CAT PTT latched down. Wait for the end of the over and try again.

You will see band setup is running for the same reason — a calibration is already adjusting the same setting.

WSJT-X has not reported an offset yet

Nothing to move relative towait

Audio offsets are moved with WSJT-X's own keyboard shortcuts, 60 Hz per press, which needs a known starting point. That comes from WSJT-X's status packets, and none has arrived yet. It clears within a T/R period of WSJT-X starting — if not, see waiting for WSJT-X.

Still stuck?

Download the diagnostics bundle from the Radio panel and open an issue. It captures versions, radio and audio device detection, live station state, recent errors and the log, with API keys redacted. If a message brought you here and this page did not answer it, that is a documentation bug worth reporting too.
